# Spring Boot + JPA로 이해하는 비관적 락 vs 낙관적 락

동시에 여러 스레드(또는 여러 서버 인스턴스)가 같은 DB 행을 동시에 수정하면 어떤 문제가 생길까요? 이 글은 간단한 "카운터 감소" 시나리오를 통해 **비관적 락(Pessimistic Lock)**과 **낙관적 락(Optimistic Lock)**의 동작 원리를 비교하고, 실제 동시성 테스트 코드로 검증해본 내용을 정리합니다.

## 프로젝트 구성

- Spring Boot 4.1.0, Java 21
- Spring Data JPA + MySQL
- 핵심 엔티티 2개
  - `DemoRow` : 락 어노테이션 없이 값(`value`)만 갖는 단순 카운터 행
  - `DemoVersionedRow` : `@Version` 필드를 가진, JPA 낙관적 락이 자동 적용되는 카운터 행

두 엔티티 모두 "값을 1씩 감소시키는" 단순한 로직을 여러 스레드가 동시에 호출했을 때, 최종 값이 정확히 계산되는지를 검증하는 것이 핵심입니다.

```java
@Entity
public class DemoRow {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int value;
}
```

```java
@Entity
public class DemoVersionedRow {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int value;

    @Version
    private Long version; // JPA가 자동으로 낙관적 락을 적용
}
```

## 비관적 락(Pessimistic Lock)이란?

**"충돌이 날 것이라고 미리 가정하고, DB 차원에서 다른 트랜잭션의 접근 자체를 막는" 방식**입니다.

- DB의 `SELECT ... FOR UPDATE` 구문을 사용해 행에 락을 겁니다.
- 락을 획득한 트랜잭션이 끝날 때까지, 다른 트랜잭션은 해당 행을 읽거나 수정하기 위해 **대기**해야 합니다.
- 즉, 여러 스레드가 동시에 요청해도 DB 레벨에서 순차적으로(줄을 서서) 처리됩니다.
- 충돌이 발생하지 않는 대신, 대기 시간(락 경합)으로 인한 성능 저하가 발생할 수 있습니다.

```java
public interface DemoRowRepository extends JpaRepository<DemoRow, Long> {

    // 비관적 락 조회 (SELECT ... FOR UPDATE)
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select d from DemoRow d where d.id = :id")
    Optional<DemoRow> findByIdForUpdate(@Param("id") Long id);
}
```

```java
@Transactional
public void decreaseWithPessimisticLock(Long id) {
    DemoRow row = demoRowRepository.findByIdForUpdate(id).orElseThrow(); // 락 획득, 다른 트랜잭션은 대기
    row.setValue(row.getValue() - 1); // 더티 체킹 대상
    demoRowRepository.saveAndFlush(row); // update 즉시 실행 후 트랜잭션 종료 시 락 해제
}
```

**언제 쓰나요?** 재고 차감, 좌석 예약처럼 충돌 가능성이 매우 높고 "실패 없이 반드시 순서대로 처리"되어야 하는 경우에 적합합니다.

## 낙관적 락(Optimistic Lock)이란?

**"충돌은 거의 없을 것이라고 가정하고, 실제로 충돌이 발생했을 때만 감지해서 예외를 던지는" 방식**입니다.

- DB 락을 걸지 않고 모든 스레드가 자유롭게 데이터를 읽고 수정을 시도합니다.
- 대신 엔티티에 `@Version` 컬럼을 두어, 조회 시점의 버전 값을 기억해둡니다.
- `UPDATE` 실행 시 `WHERE id = ? AND version = ?` 조건이 자동으로 추가되어, 조회 이후 다른 트랜잭션이 먼저 값을 바꿔 버전이 달라졌다면 **0건이 갱신**되고 Spring이 `ObjectOptimisticLockingFailureException`을 던집니다.
- 애플리케이션 코드에서 이 예외를 잡아 **재시도(retry)** 하는 방식으로 처리합니다.

```java
@Transactional
public void decreaseWithOptimisticLock(Long id) {
    DemoVersionedRow row = demoVersionedRowRepository.findById(id).orElseThrow();
    row.setValue(row.getValue() - 1);
    try {
        Thread.sleep(30); // 테스트에서 충돌을 의도적으로 유도하기 위한 지연
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    demoVersionedRowRepository.saveAndFlush(row); // version이 어긋나면 예외 발생
}
```

> 참고: 예시 코드의 `Thread.sleep(30)`은 실제 서비스 로직이 아니라, 조회와 저장 사이의 간격을 인위적으로 벌려 여러 스레드의 충돌 확률을 테스트에서 확실하게 재현하기 위한 장치입니다.

**언제 쓰나요?** 대부분의 요청이 서로 다른 데이터를 다루거나 충돌 확률이 낮은 경우(예: 게시글 수정, 프로필 수정)에 적합합니다. 락 대기가 없어 처리량이 높지만, 충돌 시 재시도 로직을 직접 구현해야 합니다.

## 비관적 락 vs 낙관적 락 비교

| 구분 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 전제 | 충돌이 자주 발생한다고 가정 | 충돌이 드물다고 가정 |
| 구현 방식 | DB `SELECT FOR UPDATE` | 엔티티 `@Version` + UPDATE 조건절 |
| 동시 접근 | 락 해제까지 대기(직렬 처리) | 자유롭게 동시 진행 |
| 충돌 처리 | 발생하지 않음(대기로 방지) | 예외 발생 → 애플리케이션에서 재시도 필요 |
| 성능 특성 | 경합이 많으면 대기시간 증가 | 경합이 적으면 빠름, 많으면 재시도 비용 증가 |

## `@Modifying`을 이용한 조건부 원자적 업데이트

락을 아예 사용하지 않고도, **DB의 원자적 UPDATE 문 자체로 동시성 문제를 해결**하는 방법도 있습니다. "값이 0보다 클 때만 감소시킨다"는 조건을 SQL의 `WHERE` 절에 포함시키는 방식입니다.

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update DemoRow set d.value = d.value - 1 where d.id = :id and d.value > 0")
int decreaseIfPositive(@Param("id") Long id);
```

이 UPDATE 문은 DB가 한 번에 원자적으로 실행하기 때문에, 애플리케이션에서 별도의 락이나 재시도 로직 없이도 "값이 음수로 내려가는 것"을 안전하게 방지할 수 있습니다. 반환값(갱신된 행 수)이 1이면 성공, 0이면 조건 불충족(이미 0 이하)으로 실패를 판별합니다.

## 테스트 코드로 검증하기

### 1. `AtomicIntegerCompareTest` — 동시성 문제의 출발점

락 이야기를 하기 전에, "왜 동시성 문제가 발생하는지"를 가장 기본적인 자바 코드 수준에서 보여주는 테스트입니다.

- `plainInt()` : 일반 `int` 변수를 두 스레드가 각각 5만 번씩 증가시킵니다. `증가`는 "읽기 → +1 → 쓰기"의 3단계로 이루어진 **원자적이지 않은 연산**이라, 두 스레드의 연산이 서로 끼어들면서 최종 값이 기대값(10만)보다 작게 나올 수 있음을 보여줍니다(race condition).
- `atomicInteger()` : 같은 로직을 `AtomicInteger.incrementAndGet()`으로 바꾸면, CAS(Compare-And-Swap) 기반의 원자적 연산이 보장되어 항상 기대값과 정확히 일치함을 확인합니다.

즉, 이 테스트는 이후 DB 락 테스트들이 왜 필요한지에 대한 **워밍업 개념 증명**입니다.

### 2. `ConcurrentToolsTest` — 멀티스레드 테스트 도구 사용법 확인

`ExecutorService`(스레드 풀)와 `CountDownLatch`(작업 완료 대기)를 조합해 다수의 비동기 작업을 실행하고, 모든 작업이 끝날 때까지 메인 스레드가 정확히 대기하는지를 검증하는 테스트입니다.

- 8개 스레드 풀로 100개의 작업을 제출(submit)
- `CountDownLatch(100)`으로 100개 작업이 모두 끝날 때까지 대기
- `AtomicInteger`로 완료된 작업 수를 안전하게 집계하여 정확히 100인지 확인

이후 나오는 락 테스트들이 공통적으로 사용하는 **동시성 테스트 패턴(스레드 풀 + 래치 + 원자적 카운터)** 자체를 검증하는 기반 테스트입니다.

### 3. `JpaLockTest` — 비관적 락 vs 낙관적 락 실전 검증

**`pessismisticLock()`**
- 초기값 50인 `DemoRow`에 대해 50개 스레드가 동시에 `decreaseWithPessimisticLock()`을 호출합니다.
- 비관적 락은 DB에서 요청들을 순서대로 처리(줄서기)하므로 충돌 자체가 발생하지 않고, 50번의 감소가 모두 성공해 최종값이 정확히 0이 되는 것을 확인합니다.

**`optimisticLock()`**
- 초기값 50인 `DemoVersionedRow`에 대해 50개 스레드가 동시에 `decreaseWithOptimisticLock()`을 호출합니다.
- 낙관적 락은 순서를 강제하지 않으므로 버전 충돌이 실제로 발생하며, `ObjectOptimisticLockingFailureException`이 잡힐 때마다 `conflicts` 카운터를 늘리고 **성공할 때까지 재시도**합니다.
- 재시도 로직 덕분에 결국 50번 모두 성공하여 최종값은 비관적 락과 동일하게 0이 되지만, 그 과정에서 여러 번의 충돌·재시도가 있었다는 점이 비관적 락과의 핵심 차이입니다.

두 테스트는 **"최종 결과는 같지만 도달하는 방식이 다르다"**는 것을 극명하게 보여줍니다. 비관적 락은 애초에 충돌이 없고, 낙관적 락은 충돌 후 재시도로 정합성을 맞춥니다.

### 4. `JpaModifyingTest` — 락 없는 조건부 UPDATE 검증

- 초기값 10인 `DemoRow`(한도 10)에 대해 40개 스레드가 동시에 `decreaseIfPositive()`를 호출합니다.
- 스레드 풀 크기는 16이지만 작업은 40개를 제출하여 충분한 동시 경합을 유도합니다.
- `WHERE value > 0` 조건 덕분에 DB가 원자적으로 갱신 성공/실패를 판별하므로, 정확히 **10개 성공, 30개 실패**가 되어야 하며 최종값은 음수로 내려가지 않고 정확히 0이 되어야 합니다.
- 이 테스트는 락(비관적이든 낙관적이든)을 전혀 쓰지 않고도 SQL 조건절만으로 동시성 문제를 해결할 수 있음을 보여줍니다.

## 정리

| 테스트 | 검증 대상 | 핵심 포인트 |
|---|---|---|
| `AtomicIntegerCompareTest` | 순수 자바 동시성 | race condition의 원인과 원자적 연산의 필요성 |
| `ConcurrentToolsTest` | 테스트 인프라 | ExecutorService + CountDownLatch 패턴 검증 |
| `JpaLockTest.pessismisticLock` | 비관적 락 | 순차 처리로 충돌 자체를 방지 |
| `JpaLockTest.optimisticLock` | 낙관적 락 | 충돌 감지 후 재시도로 정합성 확보 |
| `JpaModifyingTest` | 조건부 UPDATE | 락 없이 SQL 원자성만으로 문제 해결 |

세 가지 접근(비관적 락, 낙관적 락, 조건부 UPDATE) 모두 최종적으로는 "정확한 값"을 보장하지만, **어떻게 충돌을 다루는지**가 다릅니다. 충돌 빈도, 트랜잭션 대기 허용 여부, 재시도 로직 구현 여부 등을 고려해서 상황에 맞는 전략을 선택하는 것이 중요합니다.
